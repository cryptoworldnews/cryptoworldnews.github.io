BLS Signature Aggregation in an AVS, Step by Step

BLS signature aggregation in an AVS combines Operators’ signatures on one message into one proof, which a contract checks against quorum stake to confirm it.

Merkle Street NewsroomNov 23, 2026 · 14:51 UTC#3de9264 min read

BLS signature aggregation in an AVS combines Operators’ signatures on the same message into one signature, which an on-chain checker verifies against the quorum’s aggregate key.

Each Operator signs the message with a BLS key, and an aggregator adds those signatures together. In the eigen layer middleware, the checker also accounts for Operators who did not sign, so it can measure signed stake for a chosen quorum and block.

How does an AVS verify an aggregated BLS signature?

An AVS verifies the aggregate by rebuilding the public key for the signing Operators, then checking the signature against that key and the message. The BLS scheme supports this because adding signatures from Operators who sign the same message produces a signature verifiable against their added public keys.

At registration, Operators provide a proof of possession for their BLS public keys. This helps prevent a rogue-key attack, where a participant crafts a public key to make an aggregate appear valid without the expected signatures. The AVS or its middleware records each registered key and updates the aggregate public key for each quorum.

When a batch or other message is ready, each participating Operator signs the same message hash. The aggregator combines those individual signatures into one aggregate signature and submits it with the message hash, quorum information, non-signer public keys, and a reference block. The checker uses that block to look up the relevant quorum key and stake records.

The checker begins with the stored aggregate public key for the quorum at that reference block. It subtracts the public keys of Operators listed as non-signers. The remaining key represents the signing Operators. The contract then runs a pairing check between that key, the message, and the aggregate signature. EigenLayer middleware uses BN254, with EVM curve and pairing operations supported by the EIP-196 and EIP-197 precompiles.

The checker also calculates signed stake for each quorum: it starts with total stake at the reference block and subtracts the stake of each listed non-signer. It returns the signed stake, which the AVS compares with its configured threshold. The result is a pass or fail for the signature, plus the stake figures needed for the threshold decision.

This changes the verification work in a useful way. The contract performs one pairing check on the aggregate, rather than a separate signature verification for every signer. Its additional work for identifying signed stake grows with the non-signers: the checker must process their keys and subtract their stake. When most Operators sign, the non-signer list is short.

Say an EigenDA-style batch is signed by many Operators in a quorum. The aggregator submits the batch message and one aggregate signature. The checker reconstructs the signing key from the quorum key and the non-signers, verifies that signature, and reports signed stake for the threshold check. The batch is confirmed through one aggregate signature check, while the underlying data and the Operators’ individual participation remain distinct from that signature.

A wrong reference block can point to a different quorum key or stake snapshot, causing verification to revert. A missing non-signer key can make the reconstructed key or stake calculation inconsistent, also causing a revert or invalid result. The aggregator must submit the complete, correctly ordered non-signer data expected by the checker.

Related questions

BN254 vs BLS12-381 for AVS signing

BN254 is the curve used by EigenLayer middleware’s BLS checker, while BLS12-381 is a different pairing-friendly curve used in other systems. They are not interchangeable: keys, signatures, and pairing operations must match the curve and encoding expected by the verifier. For an AVS using this middleware, build and test against its BN254 flow.

What does an AVS aggregator do?

An AVS aggregator collects Operators’ signatures on the same message, combines them, tracks who did not sign, and submits the aggregate with the checker’s required block and quorum data. It coordinates the proof submission; the on-chain checker verifies the signature and computes signed stake.

Before integrating, confirm the checker’s expected message hash, quorum, reference block, aggregate signature, and complete non-signer list; those inputs determine whether verification succeeds and whether signed stake meets the AVS threshold.
